# Architecture

> Imported by `../CLAUDE.md` via `@docs/architecture.md`. Part of the project guidance — keep in sync with the code.

`index.html` is organized as one ~4300-line script with banner-comment section headers (`// =====` blocks). The major sections, in order:

1. **CONSTANTS & CANVAS** — fixed 480×270 pixel canvas, integer-scaled to the window via `resize()` (2× backing store, PX=2). Rendering is now the **HD vector aesthetic**: `imageSmoothingEnabled=true` and draw coords are **sub-pixel** (the old `Math.floor` pixel-snap on world/effect/sprite draws was removed, so motion is smooth and sprites are AA-softened). `imageSmoothingEnabled` only ever affected `drawImage` (unused here) — the smooth look comes from the de-floor + gradients + `'lighter'` bloom, not the flag. `const TAU = Math.PI*2` for arc draws.
2. **SPRITES** — every sprite is a `{pal, rows}` object built by `S(pal, rows)`, where `rows` is an array of ASCII strings and `pal` maps each character to a CSS color (or `null` for transparent). `drawSprite` walks the rows and `fillRect`s a 1×1 pixel per non-null character. Most entities have two frames (`_a`/`_b`) animated by a `frameT`/`frame` timer.
3. **AUDIO** — `tone()` / `noiseHit()` synthesize chiptune SFX with oscillators + filtered noise. `initAudio()` lazy-creates the `AudioContext` on the first mouse click (browsers block autoplay).
4. **LEVELS** — `LEVELS` is a **40-element** array of `{total, rate, mix, boss, bossName?, midBoss?, midBoss2?, transBoss?}`. `mix` is a weighted list consumed by `pickWeighted()` for enemy spawn rolls. **Mix weights must sum to 1.0** — `pickWeighted` does not normalize; entries past the cumulative-1.0 mark are unreachable. The boss kind for each level is in `boss`; the displayed name comes from `BOSS_NAMES[boss]` unless the level provides an override `bossName`. Bosses are assigned in **8 tiers of 5 levels each, no two tiers sharing a boss AI**: L1-L5 `bruiser`, L6-L10 `sniper`, L11-L15 `splitter`, L16-L20 `summoner`, L21-L25 `overlord`, L26-L30 `nemesis`, L31-L35 `reaper`, L36-L40 `phantom`. Every level inside a tier gets its own `bossName` so each fight feels distinct even though the AI is identical. The final boss is **L40 APOCALYPSE** (a `phantom`).
   - **STAGED BOSS ENCOUNTERS (by 10-level block).** The `midBoss`/`midBoss2`/`transBoss` fields (all **capital B**, so `validate.py` C6's lowercase `boss:` regex ignores them) drive a multi-phase encounter, tracked at runtime by the `bossPhase` state machine (globals `bossPhase`/`midbossRefs[]`/`transBossRef`, plus `midbossSpawned`/`midbossDefeated`/`bossGapTimer`/`gapSpawnTimer`; reset in `startLevel`). **L1-10**: end boss only (after the wave + most regulars dead). **L11-20**: ONE medium boss (`midBoss`) at 50% spawn progress → surge gap → end boss. **L21-30**: TWO different medium bosses (`midBoss`+`midBoss2`) simultaneously → surge gap → end boss. **L31-40**: two mediums → surge gap → ONE transitional boss (`transBoss`) → **0s** → end boss the instant the transitional dies. No two boss waves ever co-exist. The **surge gap** is `rand(10,15)`s and spawns a DENSE stream of regular monsters (alive cap 28, cadence `rate*rand(0.25,0.5)`) — not a trickle; gap monsters don't count toward `total`. The medium/transitional kinds are existing AIs reused **plus two NEW boss AIs** (`warden`, `harrier`) that are NEVER tier end bosses (so C6's locked order is untouched); each medium/trans kind differs from its level's end boss. See ENEMY AI / session-changes.
   - **Enemy/boss scaling is a FOUR-PHASE curve** (not linear), built on the shared `difficultyRamp(idx)` helper — gentle through L1-15, moderate L16-24, sharp L25-30, then a steeper **L31-40 spike** (so the late game leans on meta-progression upgrades). It is continuous at the seams and strictly increasing (the headless balance assertions + the "boss HP rises within a tier" check rely on monotonicity); the enemy ramp's per-level delta is capped at ≤0.2 by the headless continuity assertion, so most of the L31-40 spike is carried by bosses + `enemyDmgScale`, not the enemy ramp. Non-boss enemy HP/speed uses `enemyScale() = 1 + difficultyRamp(levelIdx)` (≈1.0 @L1 → ≈1.42 @L15 → ≈2.05 @L24 → ≈3.01 @L30 → ≈5.10 @L40) inside `createEnemy`. **Bosses scale on their own four-phase curves**: `spawnBoss` applies `bossHpScale(levelIdx)` (≈1.0 @L1 → ≈1.70 @L15 → ≈2.42 @L24 → ≈3.38 @L30 → ≈6.58 @L40 — phase-1 slope deliberately steeper, 0.05, so the smallest base-HP boss still rises strictly after `Math.ceil`; phase-4 slope 0.32 for the spike, uncapped by the test) and `bossSpdScale(levelIdx) = 1 + difficultyRamp*0.16` (≈1.0 @L1 → ≈1.66 @L40, flattened so bosses never get uncatchable). **`enemyDmgScale(idx)`** is a separate lever (1.0 through L30, up to ≈2.2 @L40) multiplied into the three enemy-sourced `damagePlayer` sites (gas pool, enemy bullet, enemy body) so the spike also makes hits hurt. Re-tune the whole curve from the slopes/anchors in `difficultyRamp`/`bossHpScale`/`bossSpdScale`/`enemyDmgScale`. (The headless assertion calls `bossHpScale` directly, so it can't drift.)
5. **STATE** — `STATE` enum (`MENU`, `HOWTO`, `PLAYING`, `LEVEL_COMPLETE`, `GAME_OVER`, `VICTORY`, `CHARACTER_SELECT`, `ASSISTANT_SELECT`, `SHOP`) drives both `update()` and `draw()` via dispatch on the `state` variable. Run setup flows **MENU (pick level) → CHARACTER_SELECT (pick class) → ASSISTANT_SELECT (= the LOADOUT screen: equip 0-2 owned allies + assign skills) → PLAYING**; `SHOP` (the ARMORY) is reached from a top-right button on MENU, stacked directly **under the PARAMETERS button** (`shopButtonRect` shares the PARAMETERS x/width). High score persists under `localStorage` key `shooter_high`; the **meta-progression account profile** (level/xp/gold/owned skills+assistants/loadout) persists under `shooter_profile` (`DEFAULT_PROFILE`/`loadProfile`/`saveProfile`). See the meta-progression bullet in session-changes for the full system (leveling, stat scaling, shop, loadout).
6. **INPUT** — global `keys[]` map plus a `mouse` object; mouse coords are scaled from CSS pixels back into the 480×270 logical space.
7. **ENTITY FACTORIES** — `createPlayer`, `createEnemy(kind, ...)`, `createBullet(...)`, `createPickup(...)`, and the assistant factories `createCompanion()` / `createHenchman()` / `createNunchaku()` / `createBomberAlly()` / `createPoisonAlly()` (dispatched by `createAssistant(key)`), plus the summoned `createSwordAlly(x, y)`. All entities are plain objects with a `type` field (`'player'`, `'enemy'`, `'bullet'`, `'pickup'`, `'companion'`, `'henchman'`, `'nunchaku'`, `'bomber_ally'`, `'poison_ally'`, `'sword_ally'`) and live in the global `entities` array. Dead entities set `dead:true` and are filtered out once per frame. There are **no ally singleton globals** anymore — the chosen assistants live in `entities` and are also tracked in the global `allies` array (rebuilt by `spawnSelectedAssistants`/`refreshAssistants`). NOTE: `'bomber_ally'` is distinct from the enemy boss kind `'bomber'` — do not conflate them.
8. **SPAWNING & LEVEL FLOW** — `spawnEnemyAtEdge`, `spawnBoss` (returns the spawned entity), `mediumBossKinds(L)`, `startLevel(idx)`, `startGame()`. On L1-10 the end boss spawns after `spawnedCount >= levelData.total` **and** most regular enemies have died. On L11-40 the staged `bossPhase` machine in `updatePlaying` runs first (medium wave → surge gap → optional transitional boss → end boss); see the LEVELS bullet for the full per-block sequence.
9. **UPDATE** — `update(dt)` dispatches on `state`. `updatePlaying(dt)` is the core game tick: powerup timers → player movement/aim → shooting → enemy spawn → entity update → collisions → win/loss check. **Slow-Mo powerup** is implemented by scaling `dt` only for enemies and enemy bullets (see the `enemyDt` variable) — player and player bullets keep full-speed `dt`.
10. **WEAPONS** — `fireWeapon(mx, my)` always fires the **class basic attack** (Soldier pistol / Scout blue-dot SMG / Tank slug) — powerups NEVER change its form, they only **enhance** it. The four enhancer timers stack: `rapidTime` halves cooldown, `damageTime` doubles damage, `pierceTime` sets the bullet's `pierce` flag (shots punch through), `multiTime` fires a **parallel double shot** (two bullets offset ±3 perpendicular to aim, same projectile). The old form-changing weapons (rocket/laser/homing/plasma/spread/minigun) were **removed** as player pickups — their pickup sprites (`p_rocket` etc.) and bullet sprites (`bullet_rocket`/`bullet_laser`/`bullet_plasma`) are now orphaned, but `bullet_homing` + the `homing` flag are still used by **enemy** AI. Bullet behavior flags worth knowing: `pierce` (uses `hitSet`, doesn't die on hit), `explosive` (calls `explode()`), `homing` (steers each tick — enemy-bullets toward player), `bounces` (reflects off edges; clears `hitSet` on bounce). The four weapon pickups are RAPID/PIERCE/MULTI/DAMAGE (all ~8s timed buffs); their HUD chips render in `drawHUD` stacked **above** the RMB resource bar (FUEL/ENERGY/POWER), not in the bottom `drawWeaponHUD` strip.
11. **ALLIES** — A **5-strong assistant roster** (data in `ASSISTANTS`, order in `ASSIST_ORDER`). With the meta-progression update the player now **owns** a subset (default just `drone`; the rest are bought in the SHOP) and **equips 0-2 of the owned ones** on the LOADOUT screen (`profile.equippedAssistants`, default removable — the old "exactly 2" rule is gone). `startSelectedRun` seeds `selectedAssistants = profile.equippedAssistants.slice()`; the equipped allies are spawned at run start (`spawnSelectedAssistants`) and rebuilt every level (`refreshAssistants` — survivors refilled to full HP, dead ones recreated, all repositioned at the player's side; both `.forEach` over `selectedAssistants` so 0/1/2 all work). **Each ally also has a per-account upgrade level 1..10** (`profile.assistantLevels`, raised with gold in the SHOP): `createAssistant` runs `applyAssistantLevel(a,key)` which treats the per-kind stats listed below as the **level-10 reference** and scales HP/damage/range/attack-speed down by `assistLevelFrac` (≈0.35 at L1 → 1.0 at L10) — so a fresh ally is much weaker and upgrades buy power back. **Level thresholds ALSO unlock behavioral EVOLUTIONS** (gated on `a.level` inside each AI update fn; the stat-scaling above is unchanged): **L1-3** base, **L4-6** a secondary mechanic, **L7-10** an ultimate. Drone → AoE missile every 3rd shot, then a periodic ×2-firerate berserk; brute → ground-slam (AoE+knockback), then enrage; nunchaku → whirlwind (360°+bullet-clear), then flurry; bomber → 3-bomb cluster, then carpet barrage; poison → spore nova, then plague nova. New per-ally timer fields are init'd in the factories; pulse helpers `henchmanSlam`/`nunchakuWhirl`/`bomberBomb`/`poisonNova`; all evolution spawns gate on `entities.length<480`. The SHOP/LOADOUT cards surface the current/next threshold via `assistantEvoBlurb`. Roster (base-stat lines are the **L10 reference**):
    - **`companion`** (drone, key `drone`) — auto-fires at the nearest enemy within ~280 units. AI `updateCompanion(c, dt)`. Float-follow is **speed-capped to `max(playerEffectiveSpeed*1.35, 90)`** (tracks the SPEED powerup) and clamped to `worldW/worldH` so it keeps pace on the 2×/3× arenas.
    - **`henchman`** (brute, key `henchman`) — thick HP (14), normal damage (`swingDmg 3`), large melee scope (`attackRange 40`, arc ~150°).
    - **`nunchaku`** (key `nunchaku`) — HIGH damage (`swingDmg 8`), medium scope (`attackRange 30`, arc ~108°), fast strikes (`attackRate 0.4`), 5 HP.
    - **`bomber_ally`** (key `bomber`) — fragile (3 HP); tucks behind the player and lobs a VERY-high-damage, LARGE-radius bomb (`bombDmg 10`, `explodeRadius 48`) at enemies in range. The bomb is a raw bullet object with `isGrenade + explosive` so it detonates on contact OR at end of fuse (mirrors the Soldier grenade). AI `updateBomberAlly`.
    - **`poison_ally`** (key `poison`) — 5 HP; drifts onto the nearest enemy (else escorts the player) and exudes a **wide continuous toxic aura** (`auraRadius 50`, `dps 5`) damaging every enemy inside it each tick. AI `updatePoisonAlly`. Renders a translucent green damage ring.
    - **`sword_ally`** — summoned melee knight (X-key `summon` skill, 25s cooldown, one alive at a time). The Tank also has a V-key `vsummon` variant that spawns the same knight with `attackRate` divided by 1.5 (~1.5× faster swings). Not part of the roster; spawned mid-run and stripped between levels. AI `updateSwordAlly`/`swordAllyAttack`.

    `henchman` and `nunchaku` share the generic melee AI `updateMeleeAlly(s, dt)` + `meleeAllyAttack(s)` (parameterized by `attackRange`/`attackArc`/`swingDmg`/`swingColor`/`leash`). Every ally fires/swings as `owner:'player'`. `isAlly(e)` identifies all six ally types; collisions, the entity-prune keep-list, and `startLevel`'s filter all use it (`startLevel` keeps only `player`, then `refreshAssistants` re-adds the chosen 2 — `sword_ally` is therefore dropped between levels). Each factory sets `hitInvuln` (post-hit i-frames) and `deathColor` read by the unified `damageAlly(a, amount)`.
12. **COMBAT** — `damagePlayer` (respects `shieldHp` first, then `invuln` window), the unified `damageAlly(a, amount)` (one handler for all six ally types — respects per-entity `hitInvuln`/`deathColor`), `killEnemy` (handles score, pickup drops, splitter-on-death spawn logic, boss-guaranteed drops). `killEnemy` is **idempotent** — it sets `en._killed = true` on first entry and short-circuits subsequent calls so the splitter cascade cannot fire twice when a grenade's collision hit AND its `explode()` both see the same dying enemy. Enemy-bullet collision and enemy-melee collision each scan the player plus every `isAlly(e)` entity. `explode()` is the shared AoE primitive: damages enemies in radius (operating on a **snapshot** of enemies — newly-spawned splitter children from the same blast are not re-damaged), spawns particles, and bumps `shakeTime`/`shakeAmt` (the variables still get set but `draw()` no longer applies an offset — see DRAW). `particles` is a global array hard-capped at 300 entries and reset to `[]` in both `startGame` and `startLevel`.
13. **ENEMY AI** — one update function per enemy kind: `updateSeek` (grunt/runner/tank), `updateShooter`, `updateCharger`, `updateExploder`, `updateSwarmer`, plus two newer regular kinds — **`updateWeaver`** (evasive dodger: jukes perpendicular away from the nearest incoming player bullet, else weaves in on a sine path) and **`updateSpitter`** (hazard-dropper: lays telegraphed toxic pools into the shared `groundFields` list). Boss AIs: `updateBruiser`, `updateSniper`, `updateSplitter`, `updateSummoner`, `updateOverlord`, `updateNemesis` (L26-L30), `updateReaper` (L31-L35), `updatePhantom` (L36-L40), plus `updateTwin` and `updateBomber` (reused as medium/transitional bosses) and **two NEW boss AIs used only as medium/transitional bosses**: `updateWarden` (shielded mid-range zoning turret — wide aimed fans + blink reposition + `bossInvuln`, L21+ gas) and `updateHarrier` (fast multi-dash striker — chains up to 3 dashes with brief invuln, then a radial slash; L24+ exploder packs). `updateEnemy(e, dt)` dispatches on `e.kind` and ticks down any `e.invulnT` (boss brief-invincibility) at the top. Boss telegraph attacks use a `telegraph` timer + `phase`/`phaseT` for multi-stage patterns (Overlord has 3 phases, Nemesis has 4). **Reusable boss abilities** layer onto the existing AIs, escalating by `levelIdx` and no-op for clones: `bossInvuln` (1.2s damage-absorb shield via `damageEnemy`'s `invulnT` gate; ~5.5s cd), `bossSummonExploders` (~3.5s cd), `bossSpawnClone` (a weak `isBoss:false` copy), `bossGasBomb` (a `groundFields` poison pool, ~3.5s cd), `bossHeal` (~4s cd). (These cooldowns + the per-AI telegraph timers were all shortened to make bosses more active; the `levelIdx >=` gating thresholds the headless #7 assertion keys on were NOT touched.) All enemy damage now routes through the single `damageEnemy(en, dmg, fromPlayer)` chokepoint (what makes `invulnT` work everywhere). `spawnEnemyAtEdge` runs `maybeElite(e)` to occasionally promote a spawn into a tougher/bigger **elite mini-boss** (gold halo, level-scaled chance).
14. **DRAW** — `draw()` dispatches on `state`. **Directional screen shake is enabled**: `draw()` adds a decaying offset to the camera translate (amplitude `shakeMag`, decaying over `shakeDur`, along `shakeDirX/shakeDirY` for heavy-weapon recoil or random radial otherwise); set it via the `setShake(time,mag,dx,dy)` helper (all combat sites use it), and `shakeTime` is decremented in `updatePlaying`. There's also a **hit-stop** (`hitStopTime`): `update()` skips `updatePlaying` while it ticks down but `draw()` keeps running, for a frozen-frame impact on heavy discrete hits. `drawGame()` first paints **decals** (`drawDecals()` — visual-only scorch/toxic discs, a separate capped `decals[]` array, never in `entities`), then the world, then `drawHUD`/`drawWeaponHUD` overlay UI. Two screen-space `STATE.PLAYING` overlays sit in front of the HUD: `drawPause()` (Space) and `drawStats()` (Tab — the CHARACTER STATS window of the player's live basic parameters; see systems.md). Per-type drawers: `drawPlayer`, `drawEnemy`, `drawBulletEntity`, `drawPickupEntity`, `drawCompanion`, `drawHenchman`, `drawNunchaku`, `drawBomberAlly`, `drawPoisonAlly`, `drawSwordAlly` (melee allies draw a swing-arc cone while `swingTime > 0`; `drawAllySprite(s, sprA, sprB, pipColor, halfW)` is the shared sprite+HP-bar helper). Menu / setup screens (`drawMenu`, `drawHowTo`, `drawCharacterSelect`, `drawAssistantSelect`, `drawLevelComplete`, `drawGameOver`, `drawVictory`) are click-handled in `handleMenu`/`handleCharacterSelect`/`handleAssistantSelect`/`handleLevelComplete`/`handleEndScreen` using `clickedRect`. The main menu has a `? GUIDE` button (**top-LEFT** via `guideButtonRect()`) that switches to `STATE.HOWTO` (it moved from the top-right so the profile bar can own the top-right corner).
15. **MAIN LOOP** — `loop(t)` clamps `dt` to 33ms (≈30fps floor) to keep collision math stable on tab-switches, then `update(dt); draw();`. Don't bypass this clamp from new code — without it a backgrounded tab can return a multi-second `dt` that tunnels fast bullets clean through enemies.

    `update` and `draw` are each wrapped in their **own** try/catch with a `console.error` so an exception in one cannot kill the rAF chain or freeze the canvas on a stale frame. A defensive cap also runs at the top of each frame: if `entities.length > 600`, it prunes dead entries and trims to `player` + every `isAlly(e)` entity plus the 380 most-recent others. Keep both safety nets in place when refactoring — they're cheap and they kept a real freeze-on-M bug from being totally invisible to the user.

## Adding things — quick reference

- **New enemy kind:** add a sprite pair to `SPR`, a `case` in `createEnemy`, an `update<Kind>` function, dispatch in `updateEnemy`, sprite mapping in `drawEnemy`'s switch, and (if it should appear) weight it into a level's `mix`. If it's a boss, also add an entry to `BOSS_NAMES` and a guaranteed drop in `killEnemy`'s `drops` map.
- **New equipment/powerup pickup:** add sprite + color, extend `applyPickup` with the effect, add a timer field on the player in `createPlayer` (for timed buffs), decay it in `updatePlaying`, and apply the effect where relevant (`fireWeapon`, movement, etc.). Render the icon in `drawPickupEntity` (extend both `sprMap` and `glowColors`), the HUD timer (basic-attack enhancers go in `drawHUD`'s top-left enhancer row above the RMB bar; movement/utility buffs in the bottom `drawWeaponHUD` strip), and the listing in `drawHowTo`'s `eq`/`pw` arrays. **Crucially: add the kind to the drop pool inside `killEnemy` and re-balance weights so they sum to 1.0** — the old code appended fuel after the weights already summed to 1.0, which silently gave fuel a 0% drop rate for a long time. There are **three** pools now (Tank → fuel, Soldier → beverage, Scout/default → battery); all must stay summed to 1.0 (validator C5 parses the literal `kinds`/`weights` arrays). **Drop VARIETY is then level-gated at runtime**: `killEnemy` filters the full pool to an allowed-kind set by `levelIdx` (L1-15 basics only — health/resource/rapid/shield; L16-24 adds pierce/multi/damage/speed/magnet; L25-40 the full pool) and **renormalizes** the surviving weights, and the drop-RATE base is lower early too. The static arrays still sum to 1.0, so C5 is unaffected — if you add a kind, slot it into the static pool AND into the appropriate phase's allow-set. Class-specific resource pickups (fuel, beverage, battery) live only in their owner's pool and are omitted from the generic `drawHowTo` `eq` list — they're explained on the character-select card instead. **Weapon pickups only ENHANCE the basic attack** (RAPID/PIERCE/MULTI/DAMAGE), they never replace its form — keep that invariant if adding weapon-side pickups.
- **New ally type:** factory returning `{type:'<name>', hitInvuln, deathColor, ...}`, an `update<Name>` AI function, dispatch in the main entity update loop (`updatePlaying`) and in `drawGame`, a renderer (reuse `drawAllySprite`), and — crucially — add the type to `isAlly()` so collisions / prune-cap pick it up (the unified `damageAlly` then just works). If it should be selectable, add an `ASSISTANTS` entry + `ASSIST_ORDER` key + a `createAssistant` case. Melee allies can route through `updateMeleeAlly`/`meleeAllyAttack` instead of a bespoke AI. `startLevel` keeps only `player` and re-adds the chosen assistants via `refreshAssistants`, so a non-roster ally that should persist needs its own preservation.
- **Tuning difficulty:** edit `LEVELS` (counts/rates/mix), the per-kind boss stats in `createEnemy`, and `enemyScale()` for the non-boss progression curve.

## Coordinate system

World is logical, viewport is 480×270. There are four world-size tiers, one per 10-level block, picked inside `startLevel(idx)` via `worldScale = Math.floor(idx/10) + 1`, then every tier is enlarged a further **`MAP_EXPAND = 1.15`** (1.15× linear ≈ 1.32× area) and rounded: `worldW = round(W*worldScale*MAP_EXPAND)`. **Arena AREA grows with the block** (deliberately — the late game is the most open):

- **L1-L10 (idx ≤ 9)** — 1× world, `worldW = 552, worldH = 311`. Camera now follows the player (the 1× arena is larger than the W×H viewport).
- **L11-L20 (10 ≤ idx ≤ 19)** — 2× world, `worldW = 1104, worldH = 621`. Camera follows the player.
- **L21-L30 (20 ≤ idx ≤ 29)** — 3× world, `worldW = 1656, worldH = 932`. Camera follows the player.
- **L31-L40 (idx ≥ 30)** — 4× world, `worldW = 2208, worldH = 1242`. Camera follows the player.

Each 10-level block also gets a distinct theme via `themeForLevel(idx) = THEME_ORDER[floor(idx/10)]` over `['forest','lava','ice','void']`. `drawDecor`'s `areaScale` is capped at 6× so the 4× (16×-area) arenas don't draw ~1000 decor specks/frame.

A camera follows the player on **every** tier now (all four arenas exceed the viewport after `MAP_EXPAND`). The relevant globals near the top of the script:

- `W, H` — constants, 480×270. The on-screen viewport. **Use for HUD / menu / mouse-screen-space math.**
- `worldW, worldH` — mutable, set in `startLevel(idx)`. The playable arena. **Use for entity clamps, bullet despawn/bounce, spawn-edge calculations, world-center positions, decor placement.**
- `camX, camY` — top-left corner of the camera in world space. Smoothly lerped toward `(player.x - W/2, player.y - H/2)` by `updateCamera(dt)`, clamped so the view never crosses world edges. Stays at `(0,0)` whenever `worldW === W`.

**Mouse coordinates are screen-space.** `mouse.x/y` are in `0..W, 0..H` (the visible canvas), NOT world space. To get the cursor's world position add the camera: `mouse.x + camX, mouse.y + camY`. The player aim angle and Scout's `blink` skill do this; new code that reads the cursor in gameplay must do the same.

**`draw()` flow on game states**: `ctx.save() → translate(-camX, -camY) → drawBackground(theme, idx, worldW, worldH) → drawGame()` (entities + particles only) `→ ctx.restore()`, THEN `drawHUD()` and any overlay (LEVEL_COMPLETE / GAME_OVER / VICTORY). HUD and overlays render un-translated so they stay pinned to the screen. The boss HP bar and boss-arrival flash are screen-space — they don't follow the boss across the arena. (The old "ENEMIES: N" remaining-count text was removed per request.) `drawBackground` and `drawDecor` scale their decoration counts by `(bw*bh)/(W*H)` so 2× and 3× arenas don't look bare.

`resize()` only scales the canvas element's CSS size — the backing store stays 480×270×PX and the mouse handler rescales pointer coords into the 480×270 screen space. Don't accidentally use `clientX`/`clientY` directly.
