# Session changes (recent design decisions)

> Imported by `../CLAUDE.md` via `@docs/session-changes.md`. Part of the project guidance — keep in sync with the code.

These changes are recent enough to be worth recording so future passes don't unintentionally regress them:

- **Character start-lines rebalanced: LEAN level-1 base stats + per-level growth (incl. NEW movement-speed scaling).** Player-side only — the enemy difficulty curve, XP, gold, and all validator invariants are untouched (`validate.py` C1-C10 green; headless still only the 2 pre-existing fails — drone missile, flamethrower heat — peak entities 35). The L1 base HP **and** move speed were too high (a fresh account started near its ceiling, so leveling barely changed the feel), and **soldier strictly dominated scout** (more HP, more speed, same dmg). Direction: start lean (~30% lower L1 HP+speed), then grow ~2× to the account cap so each level-up is felt.
    - **New L1 base stats** (`CHARACTERS`, hp/speed only — dmgMult/shield/sprites unchanged): tank `12→8 hp, 95→75 spd`; Leo `11→7, 120→95`; soldier `10→6, 156→110`; Ong `10→6, 140→102`; scout `9→5, 148→118`. Archetype spread preserved (survivability descends tank→scout, speed ascends tank→scout). Soldier/scout fix rides on HP+speed: soldier +1 HP, scout +8 speed — a fair trade, neither dominated.
    - **HP growth** sped up: `LVL_HP_PER 6→4`, `LVL_HP_CAP 8→9` (+1 HP every 4 account levels, max +9 by ≈L37 → caps tank 17 / Leo 16 / soldier 15 / Ong 15 / scout 14; tank is 17 not 18 because the HP bonus is uniform — bump tank base to 9 if exactly 18 is wanted).
    - **NEW movement-speed scaling** — speed used to be a fixed base (PARAMETERS showed `(+0)`). New consts `LVL_SPD_PER 1.0, LVL_SPD_CAP 35` (+1 spd/level, max +35 by ≈L36, uniform additive). Wired into `applyLevelScaling` (`p.speed += …`), `scaledStatsFor` (returns scaled `speed`), the `drawParameters` MOVE SPEED row (now `fmt(cur.speed)` + real `(+1)` delta), and the `drawCharacterSelect` card (new `spdBonus` mirrors `hpBonus`). `drawStats` (Tab) reads live `player.speed` so it auto-corrects. Caps land ≈ tank 110 / Leo 130 / soldier 145 / Ong 137 / scout 153 (±5 of the design table). `RMB_BASE_FRAC` left at 0.40 (lean theme); `LVL_DMG_*`/`LVL_FIRE_*` untouched (already per-level).
    - **Playtest note:** tank base 75 is below swarmer (78) and a charger's ~96 burst — a deliberate slow-juggernaut trade-off, offset by SPRINT (+30%→~97) and per-level growth; nudge tank base up if it plays badly.

- **Boss-hit slow-motion / hit-stop was REMOVED entirely (per user request — do NOT re-add as "juice").** Landing a hit on a boss now has **no time effect at all** — no freeze, no slow-motion, no bullet-time. This was the endpoint of several iterations the user rejected: (1) the original `hitStop` **froze the whole loop** (skipped `updatePlaying`) → read as the interface hitching/lagging; (2) scaling the **global** `updatePlaying` dt → slowed **everyone including the player** ("all characters slow down their movements — fix it"); (3) bullet-time via `enemyDt` (enemies-only slow) → still not wanted. Final: the user wants **zero** slowdown on boss hits. The boss-hit trigger in `damageEnemy`, the `triggerBossSlow` helper, the `bossSlowT`/`BOSS_SLOW_*` globals, the `enemyDt` bullet-time branch, the `updatePlaying` decrement, the `startGame`/`startLevel` resets, and headless assertion #33 were all removed; `enemyDt` is back to `dt * (slowMoTime>0 ? 0.4 : 1)`. `hitStop`/`hitStopTime`/`HIT_STOP_REFRACTORY` remain defined but are **fully vestigial** (never called), as is `damageEnemy`'s `heavy` param. The **Slow-Mo PICKUP** (`slowMoTime`, the 5 s enemies-@40% powerup) is unrelated and untouched. If a future request wants a boss-hit effect again, re-add a trigger at the `damageEnemy` `en.isBoss && fromPlayer` chokepoint — but only on explicit request.
